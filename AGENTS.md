# Agents / Dev Notes

## What this is
A fully procedural Three.js first-person walk through Sedona, Arizona at golden hour. No assets — all geometry, textures, and audio are generated in code at load time.

## How to run
```bash
docker compose -f docker-compose.base44.yml up -d
```
Then open port 3000. The page will show a black screen with loading messages for 30–60 seconds while it procedurally generates the entire scene on the GPU/CPU.

## Quirks
- **Long cold boot**: Generation takes 30–60s of blocking JS. The page is unresponsive during this time — that's expected. A *repeat* visit is much faster; see the bake store below.
- **The bake store (`src/bake.js`)**: the generated textures, the heavy geometry and the clast scatter are cached in IndexedDB (23 entries, ~108 MB), so only the first load on a given browser pays full price — 67 s cold, 7.2 s warm.
- **`buildScatter` is async and its scour list is replayed on every path.** Placement calls `terrain.addScour` (stones must sit on the bed earlier stones dug) *and* records it; `buildScatter` then calls `resetScour()` and replays the record cold or warm. If you add anything that deforms the height field during placement, it needs the same treatment or the warm load will look right and walk wrong. Three things about it are worth knowing before you debug anything odd:
  - **A code change invalidates it automatically.** The cache key carries a SHA-256 of every `src/*.js` the browser actually loaded, discovered from `performance.getEntriesByType('resource')` — so there is no file list to keep in sync, and editing any module orphans every entry on the next load. If you are ever unsure, `window.__game._clearBake()` empties it.
  - **It fails silently by design.** No IndexedDB, quota exceeded, another tab holding an older DB version — every one of those falls through to plain generation. A slow boot is a *symptom*, never a break; check `window.__game._bake` for `hits`/`misses`/`state`.
  - **Do not cache anything whose generation has side effects** unless the side effects are cached too. `buildScatter` is the standing example and the reason it is not in the store: it registers scour hollows on the height field as it places clasts, and the player's feet read those. Skipping the loop without replaying the registrations would leave the ground and the footfall disagreeing.
- **The plant maps are cached through `primePlantTextures()` (`src/plantex.js`), not through the accessors.** The six maps (bark, deadwood, foliage, grass, scrub, succulent) are memoised behind *synchronous* getters that `buildJuniper`/`buildVegetation` call from deep inside geometry helpers, so the cache cannot live in the getter without turning both builders async. `main.js` awaits the prime once — after `setPlantAnisotropy`, since anisotropy is constructor policy and not stored pixels — and the getters stay plain map reads. The cut-out maps store *every* mip level, because the expense in `coverageMips` is a 22-step binary search per level for the alpha gain that holds level zero's coverage; storing level zero alone would re-pay all of it.
- **`Growing the juniper` is three caches, not one** (2.5 s cold to 69 ms warm). The plant maps via `primePlantTextures` above; the tree's four geometries as one `bakeGeometries` entry (`juniper.geo`) because they share the branch skeleton — `clumps` comes out of `buildTree` and is what the foliage grows on, so it never escapes the producer; and `planVegetation`'s six placement lists packed into `Float32Array`s (`vegetation.plan`), ten numbers per plant. Both `buildJuniper` and `buildVegetation` are now `async`. `planVegetation` itself is still exported and untouched, which is what `tools/vegprobe.mjs` and `tools/_skyveg.mjs` import.
  - The plan cache is safe for the reason `buildScatter`'s is not: placement here only *samples* the terrain and the rocks, and registers nothing on the height field.
  - The pack narrows positions to `Float32`. Not a loss — every one of those numbers was already headed for an `instanceMatrix` or `instanceColor`, which are `Float32Array`. Both arms pack and unpack, so cold and warm are identical by construction rather than by luck.
- **A reallocated drawing buffer is a blank one: resize the canvas only immediately before a draw.** This was a live bug in the governor. `adapt()` runs from `endFrame`, so a rung change called `renderer.setSize` *after* the tick had already rendered; `setSize` reallocates both buffers, and with `preserveDrawingBuffer: false` there is nothing left to present into the new one. One solid black frame per render-scale change, worst on exactly the weak hardware the ladder exists for, since a weak GPU is one the governor keeps moving. Fixed by deferring to `pendingScale`, drained in `beginFrame` *after* the frame-cap check — before it, the drain could land on a tick that returns false and never draws, which would reintroduce the flash.
  - **What is NOT a black frame: a tick that simply doesn't draw.** `preserveDrawingBuffer: false` lets the browser *swap* buffers rather than copy them; the display buffer keeps the last frame it was given, so `setPaused(true)` and a `#fps` cap's skipped ticks hold the last image on screen rather than going black. The flag only means the *drawing* buffer's contents are undefined after a composite — which matters when you draw a partial frame, not when you draw nothing. Both of those were written up here as bugs on the strength of the flag's name alone and neither survived checking.
- **The render loop cannot be exercised headlessly.** An unfocused headless page suspends `requestAnimationFrame`, so `__game.fps` freezes at its boot value and the governor never adapts — which is why `tools/bench.mjs` pauses the loop and drives `renderOnce` by hand. Anything about frame-loop behaviour has to be verified that way or in a real browser.
- **Don't try to cache the sky: it isn't computation.** `Lighting the sky` measures ~2.5 s and stays ~2.5 s warm, which reads like an uncached stage. It isn't. `buildSky()` is 13 ms of CPU and `buildLights()` is 1 ms (measured by importing `sky.js` into a blank page on the app's origin, so `main.js` can't compete for the thread). The phase is GPU work — shader compilation and the first render of the sky shell and the shadow cascades — inflated by software rendering in a headless profile, and there is nothing in it to store. Same caution applies to any phase whose warm time equals its cold time: check whether it's CPU at all before building a cache for it.
- **Where the boot time actually is**: not in the textures, despite how much texel-by-texel loop code there is — all seven texture stages are 6.4 s of 66. The three geometry stages are 51 s. Measure before optimising.
- **Measuring a cold boot**: the timings live in `window.__game._boot` (`total`, and `phases` with per-phase ms). Call `_clearBake()` and reload, or use a fresh browser profile, or you will measure the warm path and think generation got fast.
- **No build step**: Plain ES modules with an importmap pulling Three.js from CDN.
- **No external services or secrets needed** — everything is client-side.
- The dev server is a minimal Node.js HTTP static file server in `tools/serve.mjs`.
